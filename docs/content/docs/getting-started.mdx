---
title: Getting Started
description: Set up SWE-Lego-RL and launch your first training run
---

Every workload — training, evaluation, or batch inference — follows the same five
steps:

```text
1. build the venv        bash scripts/setup_env.sh              (once per machine)
2. describe the cluster  cp lib/site.example.env lib/site.env   (once per cluster)
3. copy a template       cp train/templates/X.env train/configs/mine.env
4. validate              PREFLIGHT_ONLY=1  then  DRY_RUN=1   (checks only, nothing launches)
5. launch                bash scripts/train/train.sh train/configs/mine.env
```

Replace `train` with `eval` (score a checkpoint) or `infer` (batch trajectory
generation) for the other two workloads.

## Launch paths

Steps 1–3 are identical either way. Steps 4–5 have two equivalent paths: run the
runner by hand, or pass the config to the
[agent plugin](/docs/agent-plugin) (`/rl:*` skills for
[Claude Code](https://claude.com/claude-code)), which validates it, requires an
explicit confirmation, and launches the same runner.

| | Manual | Through the agent |
| --- | --- | --- |
| Validate | `PREFLIGHT_ONLY=1 bash scripts/train/train.sh <config>` | `/rl:check <config>` |
| Launch | `bash scripts/train/train.sh <config>` | `/rl:run <config>` |
| Watch | `tail -F logs/<exp>.log` | `/rl:status` |
| Serve the dashboard | `bash webui/start_dashboard.sh` | `/rl:dashboard` |

Both paths run the same `scripts/lib/preflight.sh`. The agent adds live-machine
checks — a run already in flight, foreign GPUs, a taken port — and a structured
verdict; see [Agent Plugin](/docs/agent-plugin).

## Prerequisites

- **8× GPU** (A100/H100-class) on the training node — on the single-node path vLLM
  serves the policy and verl runs the trainer on the same host.
- **A [sandbox backend](/docs/run-training/backends)** — a reachable
  **Kubernetes** cluster (production) or a **Docker** daemon (local or remote)
  for Harbor to run each trial in.
- **[uv](https://docs.astral.sh/uv/)** — used by `scripts/setup_env.sh` to build the
  training venv.
- **A policy checkpoint** — e.g. an SFT-trained Qwen3 model on local disk.
- **Train/val task indexes**: thin parquet
  [pointer tables](/docs/data-preparation#task-index) the trainer samples from —
  build one with `utils/create_task_index.py`, or produce a difficulty-filtered
  one with [batch inference](/docs/run-training/infer).
- **Task environment images**, prebuilt and pushed to a registry the cluster can
  reach. An unreachable image source is the most common cause of a first run that
  produces nothing but `env_setup_failed` — see
  [Site variables](/docs/reference/configuration#site-variables).

<Callout title="Run inside tmux" type="info">
A training run lasts hours. Launch it in a `tmux` session, or with `nohup setsid`,
so it survives a shell disconnect.
</Callout>

## 1. Venv

`scripts/setup_env.sh` builds the venv at `.venv` via `uv`, and clones + editably
installs `harbor` and `verl` (plus pinned veomni / vllm / flash_attn / transformers / cupy).
It is idempotent:

```bash
bash scripts/setup_env.sh
```

`harbor` is cloned to `<repo>/../harbor` and `verl` to `<repo>/../verl-swe_agent_opd_dev`.
That verl directory name is not cosmetic: `scripts/lib/common_env.sh` prepends the same
path to `PYTHONPATH` at run time, so it must be the tree that was installed. Both sides
derive it from the repo location, so a checkout anywhere works.

Key overrides (env vars): `VENV_PATH`, `HARBOR_DIR` / `VERL_DIR` (clone locations),
`HARBOR_REF` / `VERL_REF` (branches), `PYTHON_VERSION` (default `3.12.3`), and the
`SKIP_CLONE` / `SKIP_FLASH_ATTN` / `SKIP_CUPY` / `SKIP_VEOMNI` flags.

The script self-checks before it exits — veomni's training-path modules must import, and
`verl` / `harbor` must resolve to the checkouts it just installed — so a green run means a
usable venv. To confirm by hand:

```bash
.venv/bin/python -c "import harbor, verl, verl_patch; print(harbor.__file__)"
```

<Callout type="warn">
`veomni` is required by the default modeling backend (`MODELING_BACKEND=veomni`), and its
published metadata pins `datasets<=2.21.0`, contradicting verl/vllm. `overrides.txt` lifts
that bound; the installer applies it through `UV_OVERRIDE`. Installing by hand without
`--overrides overrides.txt` will fail to resolve.
</Callout>

## 2. Site config

Everything cluster-specific lives in one file, never in a run config:

```bash
cp scripts/lib/site.example.env scripts/lib/site.env
$EDITOR scripts/lib/site.env
```

Set at least `MODEL_ROOT` (checkpoint location) and `K8S_KUBECONFIG`, plus
`HARBOR_OPENSWE_IMAGE_REGISTRY` if a prebuilt-image registry exists. An empty value
is legal and falls back to the portable, slower path.
[Site variables](/docs/reference/configuration#site-variables) lists the full surface.

<Callout title="Once per cluster" type="info">
Every runner sources `site.env` automatically. No file below this step holds a cluster
address, so a run config is portable to a colleague's cluster once they write their
own `site.env`.
</Callout>

## 3. Run config

Templates are named by their **axes**: `<mode>_<backend>_<scaffold>_<model>.env`.
Copy the one matching the run into `configs/`:

```bash
ls scripts/train/templates/
#   async_k8s_ohsdk_qwen35a3b.env    sync_k8s_ohsdk_qwen35a3b.env
#   async_k8s_cc_qwen3-30b-a3b.env   sync_docker_oh_qwen3-30b-a3b.env   ...

cp scripts/train/templates/sync_k8s_ohsdk_qwen35a3b.env \
   scripts/train/configs/my_first_run.env
```

Edit only the `CHANGEME` lines — experiment name, data indexes, topology:

```bash
PROJECT_NAME=my-project
EXP_TAG=first-run
MODEL_PATH=/models/Qwen3.5-35B-A3B
TOOL_PARSER=qwen3_coder           # must match the model's chat template
TRAIN_INDEX=/data/harbor_indexes/train.parquet
VAL_INDEX=/data/harbor_indexes/val.parquet
NNODES=1
```

Everything else has a default. A knob the template does not mention takes one
`KEY=VALUE` line — see [parameter tiers](/docs/reference/configuration#parameter-tiers).

<Callout title="Smoke first" type="info">
On a new model, scaffold, or cluster, start from a smoke config (`TRAIN_BSZ=8`
`N_RESP=4`): ~8× faster per step, and it exercises the whole path. Its gradients are
noisy and its reward groups degenerate, so it is a plumbing check only, never a
learning-quality signal.
</Callout>

## 4. Validation

Every runner understands two switches. Both resolve the config, print a report, and
exit without touching a GPU or a cluster. Run them in this order:

```bash
# 1. config validation — 9 classes of fatal assertion, no cluster needed
PREFLIGHT_ONLY=1 bash scripts/train/train.sh train/configs/my_first_run.env

# 2. print the fully expanded launch command without running it
DRY_RUN=1 bash scripts/train/train.sh train/configs/my_first_run.env
```

Preflight stops on any `✗ FATAL`. It catches the mistakes that otherwise cost a
multi-hour run: a `tool_parser` that does not match the model × scaffold pair, node
counts that do not add up, an `SP_SIZE` that does not divide the training world, R3
without the new verl tree, no reachable image source.
[Preflight](/docs/run-training/preflight) lists all nine assertion classes.

The agent equivalent is `/rl:check <config>`: the same assertions plus live-machine
checks.

## 5. Launch

```bash
bash scripts/train/train.sh train/configs/my_first_run.env
```

The agent equivalent is `/rl:run train/configs/my_first_run.env`, which launches in
the background after an explicit confirmation.

The runner brings up Ray, boots vLLM, starts the in-process proxy, and drives the
PPO/GRPO/GSPO loop. On a 30B MoE at TP=4, vLLM CUDA-graph capture takes 10–20 minutes
before the first replica registers; this is expected. If a previous run left Ray or
vLLM processes behind, clear them first with `bash scripts/cleanup_before_run.sh`.

## 6. Monitoring

```bash
tail -F logs/<exp>.log
bash webui/start_dashboard.sh            # http://<host>:8090 (+ public tunnel)
```

Checkpoints land under `checkpoints/<project>/<exp>/global_step_N/`. See
[Results & Artifacts](/docs/run-training/results-and-artifacts) and
[Dashboard](/docs/dashboard).

## Other workloads

The other two workloads use the same contract: copy a template, fill the
`CHANGEME` lines, validate, run.

| Goal | Runner | Guide |
| --- | --- | --- |
| Train a policy | `scripts/train/train.sh` | this page |
| Score a checkpoint on a held-out set | `scripts/eval/eval.sh` | [Evaluation](/docs/run-training/eval) |
| Batch-generate trajectories over an index | `scripts/infer/infer.sh` | [Batch Inference](/docs/run-training/infer) |

When one host is no longer enough — large MoE policies, ~131k contexts, or
rollout-bound throughput — switch to an `async_*` template and add nodes; see
[Scaling Up](/docs/run-training/scaling).
