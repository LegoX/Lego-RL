This page defines the vocabulary you will encounter in configs, logs, and the
dashboard, and grounds each concept in the work it derives from. The system
itself is described layer by layer in [Architecture](/docs/architecture); the
complete design rationale is given in the SWE-Lego-RL technical report.

## Policy, trial, and rollout

The **policy** is the model being optimized. Two related terms are kept
deliberately distinct, following the technical report:

- A **trial** is one complete, sandboxed attempt at a task — the execution-side
  view. The agent reasons, edits files, and runs commands inside a fresh sandbox
  until it submits or reaches the turn/timeout limit.
- A **rollout** is the training-side view of the same attempt: the captured
  token sequence — prompt context, sampled assistant tokens, behavior-policy
  log-probabilities, and loss masks — that the trainer scores and optimizes.

One training step samples a batch of
`train_prompt_bsz × n_resp_per_prompt` trials across tasks
(e.g. `64 × 8 = 512` trials per step).

## Reward

Each task ships an executable **verifier** — its own test script, in the style
of SWE-bench ([Jimenez et al., 2024](https://arxiv.org/abs/2310.06770)). When a
trial finishes, the verifier runs inside the sandbox and produces a binary
outcome **reward**: `1.0` if the issue is resolved, `0.0` otherwise. Optimizing
against verified task success rather than a learned reward model removes
reward-model drift as a failure mode; what remains is protecting the verifier
itself, which is handled by the sandbox layer's anti-hacking defenses (see
[Environment](/docs/architecture/environment)). On the dashboard the reward
surfaces as `critic/score/mean`.

## Agent scaffold

The **scaffold** (the report also uses *agent harness*) is the coding agent
that drives the model through a task — Claude Code, OpenHands (ai / sdk),
OpenCode, or Terminus 2, with adapters under `src/harbor_patch/agents/`. It is
selected per run via `HARBOR_AGENT_IMPORT_PATH` and determines the rollout's
shape and which runtime image Harbor launches.

A central design constraint is that the scaffold runs **unmodified**: the
optimization target is the deployed agent's behavior, not a trainer-side
reimplementation of it. Whatever the scaffold's native protocol, it reaches the
policy through the in-process proxy described next.

## Inference chain

During training the policy serves *itself*: verl manages a pool of vLLM
replicas ([Kwon et al., 2023](https://arxiv.org/abs/2309.06180)), and every
model call a scaffold makes is routed through an **in-process proxy** that
captures the exact token-level trajectory — ids, masks, log-probabilities — at
generation time, so the trainer consumes the tokens the policy actually
produced rather than a re-tokenized transcript. The mechanism (unified
OpenAI/Anthropic surface, per-session URLs, partial-rollout handling) is
documented in [In-Process Proxy](/docs/architecture/in-process-proxy) and its
operational health checks in
[Inference Stack](/docs/run-training/inference-stack).

## Training loop

[verl](https://github.com/volcano-engine/verl) — the open-source implementation
of HybridFlow ([Sheng et al., 2025](https://arxiv.org/abs/2409.19256)) — drives
the RL loop: generate rollouts with vLLM → execute each trial in a Harbor
sandbox → collect rewards → compute advantages → update the actor (and critic,
for PPO) → sync weights.

With `TRAIN_MODE=sync` (a `sync_*` template) the trainer and the rollout engine
share the same GPUs on one node — the recommended, minimal-cost default. With
`TRAIN_MODE=async` the cluster splits into a rollout pool and a trainer pool
that run concurrently; see [Scaling Up](/docs/run-training/scaling).

### Algorithms

Selected via the `adv_estimator` / `policy_loss_mode` config variables:

- **PPO** ([Schulman et al., 2017](https://arxiv.org/abs/1707.06347)) — actor +
  critic, clipped policy-gradient objective.
- **GRPO** ([Shao et al., 2024](https://arxiv.org/abs/2402.03300)) —
  group-relative advantage estimation introduced in DeepSeekMath; no critic
  (`adv_estimator=grpo`).
- **GSPO** ([Qwen Team, 2025](https://arxiv.org/abs/2507.18071)) —
  sequence-level policy optimization (`policy_loss_mode=gspo`).

The default profile combines GRPO advantage estimation with a GSPO loss. All
three optimize over **full multi-turn rollouts**, not single completions.

## Trainer backends

verl can drive the actor on different backends, chosen by the model preset:

- **FSDP** — the default for dense models and the validated fully-async path.
- **VeOmni** — for large MoE policies (e.g. Qwen3-30B-A3B); selected with
  `USE_NEW_VERL=1` so `import verl` resolves to the
  `verl-swe_agent_opd_dev` checkout that carries the routing-replay (R3)
  wiring. Replaying rollout-time expert routing during the training forward
  pass is what keeps MoE rollout/training log-probabilities aligned (cf.
  [Ma et al., 2025](https://arxiv.org/abs/2510.11370)).
- **Megatron** ([Shoeybi et al., 2019](https://arxiv.org/abs/1909.08053)) —
  tensor/pipeline-parallel backend for the largest models.

## Sandbox backend

Every trial runs in a fresh sandbox, selected via `HARBOR_ENVIRONMENT_IMPORT_PATH`:

- **Kubernetes** — each trial is a pod; production default
  (`harbor_patch.environments.kubernetes.kubernetes:KubernetesEnvironment`,
  configured with `K8S_KUBECONFIG` / `K8S_NAMESPACE`).
- **Docker** — each trial is a local or remote container; the minimal setup, no
  cluster required (`harbor_patch.environments.remote_docker:RemoteDockerEnvironment`).

These two are validated and hardened in this stack. Because the backend is just
an import path, every environment Harbor ships is also selectable the same
way — GKE, and managed sandbox providers (Daytona, E2B, Modal, Runloop) — they
are inherited as-is and not validated here. See
[Backends](/docs/run-training/backends) for the trade-offs and config.

## Checkpoints

verl writes the actor as FSDP shards every `save_freq` steps to
`checkpoints/<project>/<exp>/global_step_N/`. These are the primary training
output and survive cleanup runs.

## The training venv

All training code runs from a single venv (default `.venv`, built by
`scripts/setup_env.sh`) with **editable** installs of `harbor`, `verl`, and this
repo itself. The editable paths must point at the trees you intend to run —
otherwise the process silently executes different code. Verify with:

```bash
.venv/bin/python -c "import harbor, verl, verl_patch; print(harbor.__file__)"
```

## Metrics

verl logs one `step:N - key:value - ...` line per step (to the launch log and
wandb). The ones to watch:

| Metric | Meaning |
| --- | --- |
| `critic/score/mean` | Mean reward (task success signal) |
| `actor/entropy` | Policy entropy — exploration / collapse |
| `actor/ppo_kl` | KL between old and new policy |
| `actor/pg_clipfrac` | Fraction of clipped policy-gradient updates |
| `perf/mfu/actor` | Model FLOPs utilization (throughput) |
| `response_length/mean` | Mean rollout length in tokens |
| `rollout_corr/kl` | Rollout-vs-training distribution shift |

The [dashboard](/docs/dashboard) renders all of these as live charts.
